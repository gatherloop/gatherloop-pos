# PRD: Order App Checkout — QRIS Payment via DOKU

**Status:** Draft for review
**Scope:** the second half of `docs/prd-table-ordering.md` — turning a customer's cart into a **paid** `Transaction` through a **QRIS** payment served by **DOKU**, with our own checkout UI.
**Supersedes:** D10 in `docs/prd-table-ordering.md` (the flagged "Pembayaran QRIS — segera hadir" stub) and the `NEXT_PUBLIC_ORDER_CHECKOUT_ENABLED` behaviour it describes.

---

## Problem Statement

`docs/prd-table-ordering.md` shipped the customer half of self-ordering: a guest scans the table QR, browses the menu, and builds a server-side cart. It stops at a stub. `libs/ui/src/presentation/views/screens/order/CheckoutScreen.tsx` renders a message saying QRIS is coming and that **the order has not been sent to the kitchen**, and `libs/ui/src/app/order/Checkout.tsx` creates nothing.

So today the feature does not actually remove the bottleneck it was built for. A guest still has to walk to the counter, re-state an order the system already holds, and pay a cashier. The cart is a nicer way to compose an order, not a way to place one.

This PRD closes the loop: **cart → QRIS payment → paid `Transaction` visible on the POS**, with the payment gateway terminating entirely inside the Go API.

### Goals

1. A guest with a non-empty cart can pay by **QRIS**, in our own UI, without leaving the order app.
2. The QR is generated by **DOKU** through our Go API. The customer bundle never talks to DOKU and never holds a DOKU credential.
3. On success the guest sees a payment-success message and is then taken to a screen telling them their order is being prepared, with their order number and table.
4. A `Transaction` exists in the POS for every successful checkout, **priced at the moment of checkout**, marked paid, with the correct wallet credited.
5. Staff can tell at a glance — and filter — which transactions came from the order app and which a cashier keyed in.
6. Every phase ships as one small, independently reviewable PR.

### Non-Goals

| Not doing | Why |
|---|---|
| Notifying barista / kitchen when an order-app transaction appears | Explicitly excluded by the requester. The transaction shows up in the existing POS list and the existing order-slip print; nothing pushes. A kitchen display or push channel is its own project. |
| Notifying the customer when their order is ready | Same. The flow ends at "sedang disiapkan". There is no customer-facing order-status polling beyond payment confirmation. |
| Any payment method other than QRIS | Requested. The gateway port is shaped so a second method is additive, but no second method is built, configured, or rendered. |
| Refunds, voids, partial payments, tips, service charge, tax lines | None exist in the POS today. A wrong order-app payment is resolved the way a wrong cashier payment is: staff `Unpay` (within 24 h) and settle by hand. |
| DOKU Checkout (hosted payment page) | Explicitly excluded — we build our own UI on the Direct API. |
| Coupons / discounts at customer checkout | `TransactionCoupon` stays a staff-only concept. Order-app transactions are created with `transactionCoupons: []`. |
| Splitting the bill, paying for someone else's table, order history | No accounts exist (the session is anonymous), so none of these have an owner. |
| Rentals through the order app | Unchanged from `prd-table-ordering.md`: the customer menu is `saleType=purchase` only. |
| POS-side QRIS (a cashier charging a walk-up guest through DOKU) | The cashier already has a physical QRIS acceptance path and books it against the `QRIS` wallet manually. Bringing that into DOKU is a separate migration with its own reconciliation story. |

### What the stub looks like today

```
libs/ui/src/app/order/Checkout.tsx                                   composition root, builds only TableResolveUsecase
libs/ui/src/presentation/handlers/order/CheckoutHandler.tsx          table shell + an `enabled` boolean
libs/ui/src/presentation/views/screens/order/CheckoutScreen.tsx      two EmptyView messages
apps/order-web/src/pages/t/[code]/checkout.tsx                       getServerSideProps → Checkout
apps/order-web/.env.example                                          NEXT_PUBLIC_ORDER_CHECKOUT_ENABLED
```

`CartScreen`'s Checkout button already routes to `/t/{code}/checkout` regardless of the flag — that was deliberate (D10), so this PRD swaps the screen's body and never touches the cart.

### The gaps this PRD must close

1. **No payment domain at all.** No gateway client, no payment records, no webhook route, no reconciliation.
2. **No way to tell a transaction's origin.** `transactions` has no `source` column; the POS list and detail screens have nowhere to show one and no filter to select one.
3. **`orderNumber` is typed by a human.** `TransactionCartView` renders it as a form field. A guest has no cashier to type it, and needs a number to collect their drink.
4. **`Transaction.name` is a customer name typed by a cashier** (the POS list searches on it, placeholder "Search Customer Name"). An anonymous guest supplies none.
5. **`Cart.Status = converted` is never set,** so a guest who pays would keep mutating the cart their payment was computed from.
6. **The API has no unauthenticated write route.** Every existing route is either `CheckAuth` (staff) or `RequireSessionId` (the guest's own cart). A gateway webhook is neither — it is an unauthenticated write authorised by a signature.

### What DOKU gives us

DOKU exposes QRIS through the Bank Indonesia **SNAP** standard (`Standar Nasional Open API Pembayaran`), Merchant-Presented Mode dynamic QR. The surface we need is four calls:

| Purpose | Method + path | Notes |
|---|---|---|
| Get access token | `POST /authorization/v1/access-token/b2b` | Headers `X-CLIENT-KEY`, `X-TIMESTAMP`, `X-SIGNATURE`. Asymmetric signature: `SHA256withRSA` over `clientId + "|" + X-TIMESTAMP` with our private key. Response carries `accessToken` and `expiresIn` (900 s). |
| Generate dynamic QRIS | `POST /snap-adapter/b2b/v1.0/qr/qr-mpm-generate` | Returns `responseCode`, `referenceNo`, `partnerReferenceNo`, `qrContent`. |
| Query payment status | `POST /snap-adapter/b2b/v1.0/qr/qr-mpm-query` | Body carries `originalPartnerReferenceNo`, `originalReferenceNo`, `merchantId`, `serviceCode: "47"`. |
| Payment notification (inbound) | DOKU → our URL, registered in the DOKU dashboard | Body carries `originalPartnerReferenceNo`, `originalReferenceNo`, `latestTransactionStatus` (`"00"` = success), `transactionStatusDesc`, `amount`. DOKU treats **any HTTP 200** as delivered. |

Transactional calls (everything but the token) are signed **symmetrically**, HMAC-SHA512 with the Client Secret over:

```
stringToSign = HTTPMethod + ":" + EndpointUrl + ":" + AccessToken + ":"
             + Lowercase(HexEncode(SHA-256(minify(RequestBody)))) + ":" + TimeStamp
```

and carry `X-PARTNER-ID` (our DOKU client id), `X-EXTERNAL-ID` (a numeric reference unique within the day), `X-TIMESTAMP`, `X-SIGNATURE`, `CHANNEL-ID` and `Authorization: Bearer <accessToken>`.

Base URLs: `https://api-sandbox.doku.com` (sandbox) and `https://api.doku.com` (production).

> **Verification note.** The egress proxy in the authoring environment blocks `developers.doku.com`, `docs.doku.com` and `sandbox.doku.com`, so the table above is assembled from DOKU's public documentation index and secondary sources, not read off the live docs. **Phase 3 must confirm every path, header name, field name and response code against the DOKU dashboard for our own merchant account before any of it is hard-coded**, and the PR description must say which page each was confirmed from. Nothing downstream of the `PaymentGateway` port depends on these details being right, which is exactly why the port exists (D2).

## UX Flow

Mobile-first, 375 px, Bahasa Indonesia, `formatRupiah()` for money — all unchanged from `prd-table-ordering.md` (D15).

**1. Cart → Checkout.** The existing sticky **Checkout** button on `/t/{code}/cart`. Unchanged.

**2. Checkout summary (`/t/{code}/checkout`).** Read-only recap: table label, line items with their options and notes, and the total. One primary button, **"Bayar dengan QRIS · Rp X"**. This screen makes the price the guest is about to be charged explicit before a QR — and therefore an amount — is locked in.

**3. QR displayed (same route, `awaitingPayment` state).** The button is replaced by:

- the QR itself, rendered client-side from `qrContent` via `react-native-qrcode-svg`, sized to fill the column width and with generous quiet space so a phone camera at arm's length can read it off another phone screen;
- the amount, large, above the QR;
- a countdown to expiry ("Selesaikan pembayaran dalam 04:32");
- copy naming QRIS explicitly ("Pindai dengan aplikasi bank atau e-wallet apa pun yang mendukung QRIS");
- a quiet, always-visible line: "Menunggu pembayaran…" with a subtle activity indicator.

The screen polls its own API for status. It never polls DOKU.

**4. Success.** The polling flips to paid. The screen shows a success state — check mark, "Pembayaran berhasil", the amount, and the assigned order number — and after ~2 seconds routes to the status screen. The delay is deliberate: an instant redirect makes a guest doubt the payment landed.

**5. Order being prepared (`/t/{code}/status?ref={reference}`).** "Pesanan Anda sedang disiapkan", the order number rendered large (it is what the guest will be called by), the table label, the paid line items and total. Terminal — nothing polls, nothing refreshes, per the non-goals. A "Pesan lagi" button returns to the menu with a fresh, empty cart.

**6. Expiry.** The countdown reaches zero: "Waktu pembayaran habis". The cart is intact and unfrozen; one button, "Coba bayar lagi", returns to state 2 and mints a new QR.

**7. Failure.** A gateway error at QR generation shows `ErrorView` with a retry that re-issues the checkout call. Nothing has been charged and nothing has been created that the guest can see.

## Confirmed Product & Technical Decisions

| # | Decision | Choice | Rationale |
|---|---|---|---|
| **D1** | Where the gateway lives | **Entirely in `apps/api` (Go).** The order app calls only our own endpoints; DOKU credentials, signing keys and the notification URL exist only on the API host. | Required by the acceptance criteria, and already the assumption `prd-table-ordering.md` was written against ("the Go API owns it — gateway secrets and payment callbacks terminate at `apps/api`, never in the customer bundle"). A browser-visible DOKU credential is a credential anyone can mint QRs with. |
| **D2** | Gateway as a domain port | `domain/payment_gateway.go` declares `PaymentGateway { GenerateQris(ctx, GenerateQrisInput) (QrisPayment, *Error); QueryQris(ctx, QueryQrisInput) (QrisStatus, *Error) }`, with `//go:generate mockgen`. `data/doku/` holds the only code that knows what DOKU is. | Every payment usecase test then runs against a mock, with no HTTP and no signing. It also means the DOKU specifics listed above being wrong costs one package, not the feature. Mirrors how `CartRepository` isolates MySQL. |
| **D3** | DOKU API flavour | **SNAP Direct API**, QRIS MPM dynamic (`qr-mpm-generate` / `qr-mpm-query`), not DOKU Checkout and not the archived non-SNAP QRIS API. | SNAP is the Bank Indonesia standard DOKU documents as current; the archived non-SNAP QRIS endpoints are labelled as such in DOKU's own docs. Building on the archived surface would buy a rewrite. **Rejected:** DOKU Checkout — the acceptance criteria require our own UI. |
| **D4** | When the `Transaction` is created | **At QR generation, unpaid**, in the same DB write as the payment record. `PayTransaction` runs when DOKU confirms. | `transaction_items` **is** the price snapshot — it already stores `price`, `productName` and the option values at creation time, which is exactly what must be frozen when an amount is locked into a QR. Creating the transaction later would mean building a second snapshot table that duplicates it. Reusing the existing unpaid → paid lifecycle also means the wallet credit, MDR and `totalIncome` math is code that already ships and is already tested. **Rejected:** create-on-success — it either recomputes prices after the fact (charging one amount and recording another when staff edit a price mid-checkout) or duplicates `transaction_items`. **Accepted cost:** an abandoned checkout leaves an unpaid transaction; D5 disposes of it. |
| **D5** | Abandoned checkouts | When a payment expires, the payment row goes to `expired` **and its transaction is soft-deleted** (`deleted_at`), which `GetTransactionList` already excludes. A late `paid` notification for an expired payment un-deletes the transaction, pays it, and logs at `warn`. | Keeps the POS list free of orders nobody paid for, without inventing a transaction status. The un-delete path exists because "expired locally, paid at DOKU" is a real race, and the money is real — the payment record, not our timer, is the authority. `DeleteTransactionById` already refuses to delete a paid transaction, so the guard is in place. |
| **D6** | How staff tell the two apart | A `source` column on `transactions`: `pos` \| `order_app`, `NOT NULL DEFAULT 'pos'`, every existing row backfilled to `pos`. Surfaced as a badge on the list item and the detail screen, and as a filter alongside the existing payment-status and wallet filters. | Requested. A column beats inferring it from `cart_id IS NOT NULL` or from the wallet: it stays correct if a future channel also uses a cart, it indexes, and it reads plainly in SQL for reporting. Defaulting to `pos` makes the migration non-breaking for every existing row and for `TransactionCreate` on the POS, which does not send the field. |
| **D7** | The order's table | `transactions.cart_id` (nullable FK) is stored alongside `source`, and the POS transaction response carries the resolved `table: PublicTable \| null`. | Without it an order-app transaction is undeliverable — staff would know an order was paid but not where to carry it. It is one nullable FK and one join through a cart that already carries `table_id`; storing `table_id` directly on the transaction would duplicate a fact the cart owns. |
| **D8** | Session ID as a capability, re-evaluated | The session ID stays the only credential, and the checkout routes stay `RequireSessionId`. What it now grants: creating a payment **for its own cart at a server-computed amount**, and reading that payment's status. It never grants spending, refunding, marking anything paid, or reading another session's payment. | D8 in `prd-table-ordering.md` required this re-evaluation. A stolen session ID can, at worst, generate a QR that the thief would then have to pay themselves and whose goods are delivered to the victim's table — not an attack, an act of charity. The state changes that move money (`paid`) are reachable **only** from a signature-verified DOKU notification or a DOKU status query, never from a client call. |
| **D9** | Charged amount authority | Computed server-side from the cart at checkout, in the same DB transaction that writes `transaction_items` and the payment row. No amount field is accepted from the client, on any route. | Continues D7 of `prd-table-ordering.md`. Once the QR exists the amount is immutable — a later price edit by staff cannot change what the guest is being asked to pay, and cannot change what the transaction records. |
| **D10** | Cart freeze | While a payment for a cart is `pending` and unexpired, every `/carts/current*` **write** returns `400` (`bad_request`, "cart is locked by a pending payment"). Reads are unaffected. `expired` or `failed` unlocks it; `paid` converts it. | The cart is the thing the amount was computed from. Letting a guest add an item to a cart whose QRIS QR is on screen produces an order that is either underpaid or mis-prepared. The freeze is the smallest correct answer, and it is naturally released by the expiry the guest can already see counting down. |
| **D11** | One QR per cart | `POST /carts/current/checkout` is idempotent: with a `pending`, unexpired payment on the active cart it returns **that** payment rather than minting a second one. | A double-tapped button or a reloaded screen must not produce two QRs for one order — two QRs means two possible payments for one set of drinks. |
| **D12** | Learning that payment succeeded | **Both**: DOKU's notification webhook is the primary path; the order app polls `GET /payments/{reference}` every 3 s while `pending`, and that read **re-queries DOKU** (`qr-mpm-query`) when the payment is still `pending` and its status was last checked more than 10 s ago. | A webhook we do not control is a single point of failure, and its absence is silent — the guest would stare at a paid QR and a spinner. The poll's re-query makes the webhook an optimisation rather than a dependency. The 10 s floor keeps a rapid client poll from becoming a rapid DOKU poll. |
| **D13** | Notification authentication | The route is unauthenticated but **signature-verified**: the symmetric HMAC-SHA512 scheme, recomputed over the received body, compared in constant time; a skewed or missing `X-TIMESTAMP` (> 5 min) is rejected. A rejected notification is `401` and is logged with the reference number. | It is the only unauthenticated write in the API, and it is the one that marks money received. Its own middleware (`VerifyDokuSignature`), sitting beside `CheckAuth` and `RequireSessionId`, keeps that fact legible in `*_route.go` instead of buried in a handler. |
| **D14** | Notification idempotency | The handler is keyed on `partner_reference_no`. A notification for a payment already `paid` is a no-op returning `200`. Transitions are one-way: `pending → paid \| expired \| failed`, and `expired → paid` only via D5. | DOKU retries until it sees a 200, so duplicates are expected traffic, not an error. Paying a transaction twice would credit the wallet twice — `PayTransaction` already guards with "transaction already paid", and this is the second lock. |
| **D15** | Which wallet the money lands in | A configured wallet id, `ORDER_PAYMENT_WALLET_ID`, pointed at the existing `QRIS` wallet. Validated at startup: unset, unknown, deleted, or `is_payment_target = false` fails the boot with a named error. | `PayTransaction` already credits a wallet and subtracts its `paymentCostPercentage`, which is precisely the DOKU MDR — so settlement accounting is configuration, not code. Failing at boot rather than at the first checkout means a misconfiguration is found by a deploy, not by a guest holding a phone. **Rejected:** matching a wallet by the name `"QRIS"` — a rename would silently redirect revenue. |
| **D16** | `orderNumber` for order-app transactions | Assigned server-side as `MAX(order_number) + 1` over transactions created **today** (both sources, deleted rows included), inside the checkout DB transaction. Cashier-entered numbers are untouched. | The guest needs a number to be called by, and there is no cashier to type one. Sharing the counter's daily sequence is what keeps the two channels callable from one queue. **Accepted:** `order_number` has no unique constraint today and a cashier can still type a colliding number — pre-existing behaviour, not introduced here, and visible to staff on the same list. |
| **D17** | `Transaction.name` for order-app transactions | The **table label** ("Meja 1"). | The column is a free-text label the POS list searches ("Search Customer Name") and the order slip prints. An anonymous guest has no name; the table is the only identity the order has, and it is the one staff need. Leaving it empty would make every order-app row render as an untitled list item. |
| **D18** | Where the payment reference lives in the URL | The status screen is `/t/{code}/status?ref={partnerReferenceNo}`, and `partnerReferenceNo` is `ORD` + 13 random Crockford base32 characters from the existing table-code generator — never a sequence. | The reference must survive the cart converting (after which `GET /carts/current` returns a fresh empty cart and can no longer reach the payment). Putting it in the URL makes reload and back work. Reads are still scoped by `X-Session-Id`, so the random reference is defence in depth, not the lock — but a sequential id in a URL invites enumeration and there is no reason to offer it. |
| **D19** | The webhook route in `api.yaml` | It is declared in `libs/api-contract/src/api.yaml` like every other route, tagged `payment`. The generated TS client function for it is never imported. | `api.yaml` is the single source of truth the Go models are generated from too; a hand-written request struct for the one route that parses untrusted input is the wrong place to break that rule. The unused client export tree-shakes away. |
| **D20** | Feature flag | `NEXT_PUBLIC_ORDER_CHECKOUT_ENABLED` survives and keeps its meaning as the kill switch: `false` renders "Checkout belum tersedia" exactly as today, `true` renders the real checkout. It stays `false` until phase 11. | The flag already exists, `CartScreen` already routes through it, and every phase before the last can therefore merge to `main` and deploy without a guest ever reaching a half-built checkout. |
| **D21** | Sandbox vs production | Environment-selected via `DOKU_BASE_URL` plus its own credential set. The sandbox is what CI, local development and manual QA use; production credentials exist only in the API host's systemd `EnvironmentFile`. | The DOKU merchant account has distinct credentials per environment; making the base URL configuration rather than a build flag means promoting to production is an env change and a dashboard webhook registration, not a code change. |
| **D22** | Where the checkout frontend code lives | `libs/ui`, under the existing order slices, reached through `@gatherloop-pos/ui/order` (D20 of `prd-table-ordering.md`). `apps/order-web` gains two thin pages. | Unchanged from every other order-app slice. No new library, no new entry point. |

## Feature Requirements

### FR-1 — `source` and `cart_id` on `Transaction` (API)

Migration `000023_add_transaction_source` (next free number; latest is `000022_add_product_variant_recipe`):

```sql
ALTER TABLE `transactions`
  ADD COLUMN `source`  VARCHAR(16) NOT NULL DEFAULT 'pos' AFTER `name`,
  ADD COLUMN `cart_id` BIGINT      NULL                   AFTER `source`,
  ADD KEY `idx_transactions_source` (`source`),
  ADD KEY `idx_transactions_cart_id` (`cart_id`),
  ADD CONSTRAINT `fk_transactions_cart` FOREIGN KEY (`cart_id`) REFERENCES `carts` (`id`);
```

`VARCHAR(16)` with a plain string value matches how `saleType`, `station` and `carts.status` are already modelled. The `.down.sql` drops the constraint, the keys, then the columns.

- `domain.Transaction` gains `Source TransactionSource` (`TransactionSourcePos` / `TransactionSourceOrderApp`) and `CartId *int64`, `Cart *Cart`.
- `TransactionRequest` in `api.yaml` is **unchanged** — the POS never sends a source, and `CreateTransaction` defaults an empty source to `pos`, so the existing POS create path is untouched.
- `Transaction` in `api.yaml` gains required `source` (`enum: [pos, order_app]`) and optional `table: PublicTable`.
- `GET /transactions` gains an optional `source` query parameter (`pos` \| `order_app` \| `all`, default `all`), threaded through `GetTransactionList` / `GetTransactionListTotal` the way `paymentStatus` and `walletId` already are.
- The restapi transformer resolves `table` from `cart_id → carts.table_id → tables` and returns `null` for POS transactions.

Handler tests assert: an existing (`pos`) transaction serialises as `source: "pos"`; the `source=order_app` filter excludes POS rows; `POST /transactions` without a source still creates a `pos` transaction.

### FR-2 — POS surfaces the source (frontend)

- `TransactionListItem` renders a badge when `source === 'order_app'` — label "Order App", and the table label from `table` when present. POS transactions render no badge, so the existing list is visually unchanged.
- `TransactionList`'s filter popover gains a **Source** radio group (`All` / `POS` / `Order App`) beside the existing wallet and payment-status controls.
- `transactionList` usecase params and the `transactionListQuery` URL repository carry `source`, so the filter is bookmarkable exactly as the existing filters are.
- `TransactionDetail` shows a Source row, and the table label when present.
- Stories for both new states on `TransactionListItem` and `TransactionDetail`; mobile parity via the shared components (`pos-mobile` renders the same list item).

### FR-3 — Payment gateway port and DOKU client (API)

`domain/payment_gateway.go`:

```go
type QrisPayment struct {
    PartnerReferenceNo string
    GatewayReferenceNo string
    QrContent          string
    ExpiredAt          time.Time
}

type QrisStatus struct {
    PartnerReferenceNo string
    GatewayReferenceNo string
    Status             PaymentGatewayStatus // pending | paid | expired | failed
    PaidAmount         float32
    RawStatusCode      string
}

type PaymentGateway interface {
    GenerateQris(ctx context.Context, input GenerateQrisInput) (QrisPayment, *Error)
    QueryQris(ctx context.Context, input QueryQrisInput) (QrisStatus, *Error)
    VerifyNotificationSignature(method, path string, headers NotificationHeaders, body []byte) *Error
    ParseNotification(body []byte) (QrisStatus, *Error)
}
```

`data/doku/` implements it:

- `client.go` — base URL, HTTP client with an explicit 10 s timeout, structured logging of every call with the reference number and **never** the signature, secret, private key or access token.
- `token.go` — the B2B access token, cached in memory with a margin (refresh at `expiresIn - 60s`), guarded by a mutex, refetched once on a `401`.
- `signature.go` — the asymmetric (`SHA256withRSA`) and symmetric (`HMAC-SHA512`) schemes, plus the JSON minifier the symmetric digest is computed over. Signature verification uses `hmac.Equal`.
- `qris.go` — `qr-mpm-generate` and `qr-mpm-query`, mapping DOKU response codes to `PaymentGatewayStatus` and DOKU errors to `domain.Error`.

Tests are `httptest`-based and cover: token caching and refresh; a signature computed against a fixed vector; `2004700`-shaped success mapped to `QrisPayment`; `latestTransactionStatus` `"00"` → `paid`, expiry/failure codes → `expired` / `failed`, anything unknown → `pending` (never optimistically `paid`); a notification with a tampered body rejected; a notification older than 5 minutes rejected.

Configuration in `utils/env.go` (all read once, all required when checkout is enabled): `DOKU_BASE_URL`, `DOKU_CLIENT_ID`, `DOKU_CLIENT_SECRET`, `DOKU_PRIVATE_KEY` (PEM), `DOKU_MERCHANT_ID`, `DOKU_CHANNEL_ID`, `DOKU_QRIS_EXPIRY_SECONDS` (default 900), `ORDER_PAYMENT_WALLET_ID`.

### FR-4 — `order_payments` (API)

Migration `000024_create_order_payments`:

```sql
CREATE TABLE IF NOT EXISTS `order_payments` (
    `id`                   BIGINT       NOT NULL AUTO_INCREMENT,
    `cart_id`              BIGINT       NOT NULL,
    `session_id`           CHAR(36)     NOT NULL,
    `transaction_id`       BIGINT       NULL,
    `partner_reference_no` VARCHAR(64)  NOT NULL,
    `gateway_reference_no` VARCHAR(64)  NOT NULL DEFAULT '',
    `method`               VARCHAR(16)  NOT NULL DEFAULT 'qris',
    `status`               VARCHAR(16)  NOT NULL DEFAULT 'pending',
    `amount`               FLOAT        NOT NULL DEFAULT 0,
    `qr_content`           TEXT         NULL,
    `expired_at`           DATETIME     NOT NULL,
    `paid_at`              DATETIME     NULL,
    `status_checked_at`    DATETIME     NULL,
    `created_at`           DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    `updated_at`           DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    `deleted_at`           DATETIME     NULL,
    PRIMARY KEY (`id`),
    UNIQUE KEY `uq_order_payments_partner_reference_no` (`partner_reference_no`),
    KEY `idx_order_payments_cart_id_status` (`cart_id`, `status`),
    KEY `idx_order_payments_session_id` (`session_id`),
    CONSTRAINT `fk_order_payments_cart`        FOREIGN KEY (`cart_id`)        REFERENCES `carts`        (`id`),
    CONSTRAINT `fk_order_payments_transaction` FOREIGN KEY (`transaction_id`) REFERENCES `transactions` (`id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

Notes: no raw-notification blob column — the notification is logged, not stored, because it can carry payer identifiers we have no purpose for and no retention policy about. `status_checked_at` is what implements D12's 10 s floor. `method` exists so a second method is a value, not a migration; only `qris` is ever written.

Domain entity `OrderPayment`, `OrderPaymentRepository` (with `//go:generate mockgen`), MySQL repo + transformer, repo tests — following the `cart` slice exactly.

### FR-5 — Checkout endpoints (API)

All session routes require a valid `X-Session-Id` (`RequireSessionId`, unchanged).

| Method | Path | Body | Behaviour |
|---|---|---|---|
| `POST` | `/carts/current/checkout` | — | Creates the transaction (unpaid) + payment (pending) and returns the payment with `qrContent`. Idempotent per D11. |
| `GET` | `/payments/{partnerReferenceNo}` | — | Returns the payment. `404` unless `payment.session_id` matches the header. Re-queries DOKU per D12. |
| `POST` | `/payments/doku/notification` | DOKU SNAP notification | Signature-verified (D13), idempotent (D14). Always `200` once the signature is valid. |

`POST /carts/current/checkout`, in one DB transaction:

1. Load the session's active cart. Empty cart ⇒ `400` "cart is empty". No table attached ⇒ `400` "table is not set".
2. A `pending`, unexpired payment on this cart ⇒ return it and stop (D11).
3. Compute the total from current variant prices (D9).
4. Assign `orderNumber` per D16 and `name` per D17.
5. `CreateTransaction` with `source = order_app`, `cartId`, one `TransactionItem` per cart line (`variantId`, `amount`, `note`, `discountAmount: 0`), `transactionCoupons: []`. This snapshots price, product name and option values.
6. Mint `partnerReferenceNo` (D18); insert the payment row `pending` with `expired_at = now + DOKU_QRIS_EXPIRY_SECONDS`.
7. Call `PaymentGateway.GenerateQris`. On error the whole DB transaction rolls back — no orphan transaction, nothing to reconcile — and the endpoint returns `502` `internal_server_error`.
8. Store `qrContent` and `gatewayReferenceNo`; return the payment.

The cart is **not** converted here — only a paid payment converts it (D10).

`GET /payments/{partnerReferenceNo}`: if `status = pending` and `status_checked_at` is null or older than 10 s, call `QueryQris` and apply the result through the same state transition used by the notification handler, so both paths share one code path and one set of guards. Response carries `partnerReferenceNo`, `status`, `amount`, `qrContent`, `expiredAt`, `paidAt`, `orderNumber`, `tableLabel`, and the paid line items — enough for the status screen to render without a second call.

`POST /payments/doku/notification`:

1. `VerifyDokuSignature` middleware. Invalid ⇒ `401`, logged with the reference.
2. Parse to a `QrisStatus`; unknown `partnerReferenceNo` ⇒ `200` with a `warn` log (never `404` — a `404` makes DOKU retry a notification we can never handle).
3. `paid` and payment already `paid` ⇒ `200`, no-op (D14).
4. `paid` and payment `pending` or `expired` ⇒ in one DB transaction: un-delete the transaction if D5 soft-deleted it; `PayTransaction(walletId = ORDER_PAYMENT_WALLET_ID, paidAmount = payment.amount, transactionId)`; set the payment `paid`, `paid_at`; set the cart `converted`.
5. `expired` / `failed` ⇒ payment status set, transaction soft-deleted, cart left `active` and thereby unfrozen.
6. `200` in every case where the signature was valid.

**A mismatched amount is a hard stop.** If the notification's amount differs from `payment.amount`, nothing is paid: the payment is left `pending`, the event is logged at `error` with both amounts, and the response is still `200`. Staff reconcile by hand. Silently accepting a different amount than the one we recorded is how a reconciliation bug becomes a revenue bug.

### FR-6 — Cart freeze (API)

`CartUsecase.AddCartItem`, `UpdateCartItem`, `RemoveCartItem`, `ClearCart` and `UpdateCartTable` first check for a `pending`, unexpired payment on the active cart and return `400` `bad_request` "cart is locked by a pending payment" if one exists. `GetCurrentCart` is unaffected.

Usecase tests cover each mutation against a locked and an unlocked cart, and that an expired pending payment does not lock.

### FR-7 — Frontend payment slice (domain + data)

Per the file inventory in `prd-table-ordering.md`:

- `domain/entities/OrderPayment.ts` — `{ reference, status: 'pending' | 'paid' | 'expired' | 'failed', amount, qrContent, expiredAt, paidAt, orderNumber, tableLabel, items }`.
- `domain/repositories/orderPayment.ts` — `OrderPaymentRepository { checkout(): Promise<OrderPayment>; fetchPayment(reference): Promise<OrderPayment> }`.
- `data/api/orderPayment.ts` + `.transformer.ts`, and `data/mock/orderPayment.ts`. The API repository takes a `SessionRepository` and attaches `X-Session-Id` with `withCredentials: false`, exactly as `ApiCartRepository` does.
- `domain/usecases/checkout.ts` — the state machine:

```ts
type Context = {
  payment: OrderPayment | null;
  errorMessage: string | null;
};

export type CheckoutState = (
  | { type: 'idle' }              // summary shown, nothing requested yet
  | { type: 'creatingPayment' }   // POST /carts/current/checkout in flight
  | { type: 'awaitingPayment' }   // QR on screen, polling
  | { type: 'paid' }
  | { type: 'expired' }
  | { type: 'error' }
) & Context;

export type CheckoutAction =
  | { type: 'CHECKOUT' }
  | { type: 'CHECKOUT_SUCCESS'; payment: OrderPayment }
  | { type: 'CHECKOUT_ERROR'; message: string }
  | { type: 'POLL' }
  | { type: 'POLL_SUCCESS'; payment: OrderPayment }
  | { type: 'POLL_ERROR'; message: string }
  | { type: 'EXPIRE' };
```

`onStateChange` owns the 3 s poll while `awaitingPayment` and clears it on every other state. A `POLL_ERROR` does **not** leave `awaitingPayment` — a dropped poll on a café network must not tell a guest their payment failed; it is logged and the next tick retries. Only an explicit `expired`/`failed` status, or the local countdown reaching `expiredAt`, leaves the state.

`checkout.test.ts` covers, via `UsecaseTester` with `MockOrderPaymentRepository`: `idle → creatingPayment → awaitingPayment`; `awaitingPayment → paid`; a poll error keeping `awaitingPayment`; `awaitingPayment → expired` on both the server status and the local countdown; `creatingPayment → error` and retry.

## Non-Functional Requirements

| Area | Requirement |
|---|---|
| Secrecy | No DOKU secret, private key, access token or signature is ever logged, returned in an error body, or sent to any frontend. Log lines carry `partnerReferenceNo` and status only. |
| Latency | Checkout (`POST /carts/current/checkout`) completes in < 3 s at p95, including the DOKU round trip. Outbound DOKU calls time out at 10 s. |
| Correctness | A guest is never charged twice for one cart (D11), and one payment never pays two transactions (D14). A payment is `paid` only on a signature-verified notification or a DOKU status query — never on client input. |
| Availability | A DOKU outage degrades to a visible error at QR generation. Nothing is created and nothing is charged. A webhook outage alone is invisible to the guest, because polling re-queries DOKU (D12). |
| Observability | Structured logs at each state transition; `warn` on an unknown reference or a late notification for an expired payment; `error` on a signature failure or an amount mismatch. |
| Testing | Go usecases against `mockgen` mocks; the DOKU client against `httptest`; frontend usecases through `UsecaseTester` with mock repositories; handlers through Testing Library; screens through Storybook; the whole flow through Playwright with a stubbed gateway. |
| Data | No cardholder data, no payer identity, and no notification body is persisted. `order_payments` holds only what reconciliation needs. |

## Success Metrics

1. **Checkout completion rate** — payments reaching `paid` ÷ payments created. Target > 80% within two weeks of enabling the flag; below that, the QR presentation or the expiry window is wrong.
2. **Orphan rate** — payments `paid` at DOKU whose transaction is not `paid` in our DB. Target **zero**; any occurrence is a P1.
3. **Webhook dependency** — share of payments confirmed by the poll's DOKU re-query rather than by the notification. A high share means the webhook registration or delivery is broken even though guests are unaffected.
4. **Counter load** — order-app share of daily transactions (`source = order_app`), the number the whole feature exists to move.

## Risks and Mitigations

| Risk | Mitigation |
|---|---|
| The DOKU API details in this document are wrong (docs unreachable while authoring) | Everything DOKU-shaped is behind `PaymentGateway` (D2) and lands in one phase (3) whose acceptance criterion is a successful sandbox round trip. A wrong path or field name costs that PR, not the design. |
| The notification never arrives (misregistered URL, DOKU outage, our host unreachable) | Polling re-queries DOKU (D12), so confirmation does not depend on it. Metric 3 makes silent breakage visible. |
| Notification arrives after we expired the payment locally | D5's un-delete-and-pay path, logged at `warn`. The payment record, not our timer, is the authority. |
| Guest pays, then our DB write fails | The payment stays `pending` and both the next poll and any notification retry re-attempt the same idempotent transition (D14). A permanent failure surfaces as a nonzero metric 2 and is reconciled from the DOKU dashboard by reference. |
| A price changes between QR generation and payment | The amount and the line prices are frozen in `transaction_items` at generation (D4/D9). The guest pays what they were shown. |
| Cart frozen and never released (a payment stuck `pending` because DOKU never answers) | `expired_at` is set at generation and always in the past eventually; the freeze check treats an expired pending payment as unlocked (FR-6), so the cart releases without any sweeper running. |
| Auto-assigned order number collides with a cashier-typed one | Pre-existing: `order_number` has never been unique. Both rows are on the same list with distinct source badges. Noted, accepted (D16). |
| Wallet misconfiguration books revenue to the wrong wallet | Boot-time validation of `ORDER_PAYMENT_WALLET_ID` against existence, soft-deletion and `is_payment_target` (D15). |
| Abuse: someone mints QRs in a loop | Each QR is scoped to one cart with one pending payment (D11), so the ceiling is one QR per session per expiry window. Rate limiting remains out of scope (D12 of `prd-table-ordering.md`), still noted. |
| MDR mis-booked, understating income | `paymentCostPercentage` on the configured wallet is the single MDR input, and `PayTransaction` already applies it. Verify the configured percentage against the DOKU merchant agreement in phase 11. |

---

## Open Questions

1. **DOKU merchant account** — do we hold production credentials, or sandbox only? Phase 3 can complete on sandbox alone; phase 11 cannot.
2. **QR expiry window** — 15 minutes is the assumed default. Is a shorter window (5 min) better for table turnover, given that expiry unfreezes the cart and re-checkout is one tap?
3. **MDR** — what `paymentCostPercentage` does our DOKU QRIS agreement imply, and is the existing `QRIS` wallet already set to it?
4. **Settlement timing** — DOKU settles T+1 or later, but `PayTransaction` credits the wallet immediately. Is same-day wallet balance the behaviour finance wants, or should order-app revenue land in a "DOKU (belum settle)" wallet and be transferred on settlement? This changes only `ORDER_PAYMENT_WALLET_ID` and a manual transfer habit, so it does not block any phase.
5. **Minimum order amount** — QRIS has practical floors per issuer. Should checkout reject a cart below some threshold with a clear message rather than surfacing a gateway error?
